# headless-agents 0.5.4 — design

- **Date**: 2026-10-02
- **Status**: spec approved (Q120); amendment 1 (§7) approved (Q124)
- **Scope**: brain ticket 56ce46f2 (items deferred from 0.5.3) and ticket 925b07b6
- **Operator decisions**: Q98 (method `spec`), Q105 (scope), Q107 (one verb), Q108 (a
  separate journal file), Q116 (design approved)

## 1. Problem

0.5.3 ships a quarantine refusal that names a manual lifting procedure, but no command
performs it. A write that ends compromised or pending leaves its lineage, its quarantine
and sometimes a stale unconfined intent behind. Until someone renames ha's private state
files by hand, every later write on the repository is refused. `ha clean --force` was
written for 0.5.3 and removed after four review rounds on brain-v42 PR #246. Each round
found a new way an interrupted or replayed cleanup could destroy the wrong thing (decision
23307333). The cleanup must survive interruption, so it needs a journal of idempotent
steps with recorded expectations, not one more patch.

Smaller deferred items ride along:

- `ha init` presets (lot 6).
- An unknown model id fails with an opaque provider error.
- `ha models` gives up without a catalogue.
- No proof says whether a rail lets a write open a loopback socket.
- `keys.py` echoes a value and leaks two exception types.
- Ticket 925b07b6 (a refused new lineage unlinked without the registry lock) turned out already fixed in v0.5.3 (§3.6).

## 2. Decisions

| # | Decision |
|---|---|
| D1 | One command retires an uncertain lineage: `ha clean --force RUN [--keep-branch]` (Q107). No `ha abandon`. |
| D2 | Its progress lives in a journal file, `<state>/cleanups/<owner>.json`, published before the first destructive step (Q108). |
| D3 | `ha clean --force` lifts lineage state under the lineage registry lock held exclusive, taken before the lineage lock (rank order) and held for the whole command. Ticket 925b07b6 is already fixed in v0.5.3 (§3.6). |
| D4 | `ha init` follows the 0.5.3 spec's lot 6 and its decision D2: no model names. It uses the names of red-skills decision 35521a0d. |
| D5 | The loopback proof is recorded and shown, never gating. |
| D6 | The first real `ha providers --update` (ticket item 5) is a machine gesture, out of the code scope. It gets its own operator question when the release evidence is gathered. |

### 2.1 Background facts the design relies on

- `ha clean RUN` today (`engine.clean`, `write_flow.clean_write`):
  - It takes the run's lifecycle lock without waiting, then the global admission shared.
  - For a lineage member, it then takes the registry lock shared and the lineage lock
    exclusive.
  - It refuses with no git command at all when a quarantine covers the repository, when
    an unconfined intent is stale, or when the lineage is compromised or pending.
  - Otherwise it removes the worktree and the run directory, and keeps the branch and the
    lineage state.
- Lineage state is spread over several places:
  - `<state>/lineages/<owner>.json` holds `owner`, `repository`, `common_dir`,
    `worktree`, `branch`, `base`, `members`, `pending`, `compromised` and
    `compromised_history`.
  - `<state>/lineages/<owner>.lock` is the lineage lock, and `<state>/lineages.lock`
    the registry lock.
  - Each member has a run record, `<state>/runs/<id>.json`.
  - The worktree is `<owner run_dir>/wt`, on branch `ha/<owner>`.
- Quarantine files live at `<state>/quarantine/repo-<sha256(common_dir)[:16]>.json` and
  `<state>/quarantine/operator.json`. Each holds `scope`, `reason`, `run_id`, `paths` and
  `common_dir`; the first quarantine published wins. A lineage-scoped quarantine has no
  file: the lineage carries `compromised`.
- The unconfined intent lives in `<state>/unconfined-intent.json`, with
  `<state>/unconfined-writers.json` beside it. A stale intent re-publishes the operator
  quarantine on the next write.
- The README's manual procedure, which `ha clean --force` automates:
  1. Remove the worktree.
  2. Delete the branch, after checking it holds nothing worth keeping.
  3. Lift a stale unconfined intent before the quarantine.
  4. Rename the state files to `*.lifted-<UTC ts>`, all with one timestamp, and never
     delete them.

## 3. Design

### 3.1 `ha clean --force` — when it acts

`RUN` may be any member of the lineage. The owner is resolved as follows:

- From the run's registry entry (`entry.lineage`).
- If the registry entry was already lifted by an interrupted cleanup, from the journal
  `<state>/cleanups/*.json` whose `members` lists `RUN`. A journal file whose name and
  `owner` field disagree is refused.

`--force` acts only on an **uncertain** lineage, one of:

- `compromised` is set.
- `pending` is set.
- A repository or operator quarantine's `run_id` is one of the lineage's members.
- An unfinished journal exists for it (resume).

On a healthy lineage, `--force` refuses (exit 1) and names plain `ha clean`, which keeps
the branch. `--keep-branch` is accepted only with `--force`.

A plain `ha clean` refusal on an uncertain lineage now names
`ha clean --force <run>` instead of the manual procedure. The README keeps the manual
procedure as the fallback for a cleanup that itself refuses.

### 3.2 Locks

Taken in the existing rank order (`locks.Rank`, enforced by `_check_order`: a lock of a
lower rank is never taken while a higher one is held, and only `LINEAGE` locks stack), and
held until the command ends:

1. **The lifecycle lock of `RUN`**, without waiting, as plain `ha clean` takes it. An
   active run refuses with `<id> is active: nothing cleaned`. Only one `LIFECYCLE` lock
   can be held; every other member's lifecycle lock is probed with `locks.is_free` once
   step 2 is admitted, and a held one refuses the same way. No member can start
   afterwards: every run needs the global admission this command holds exclusive.
2. **The global admission, exclusive**, through the admission queue labelled `clean`, as
   an unconfined write is. Nothing else runs while a lineage is retired, so no run can
   list, load or re-quarantine the state being lifted. A waiting admission behind it
   reads the queue as usual. The bound is the default admission bound
   (`LOCK_WAIT_SECONDS`); `ha clean` gains no `--wait` flag.
3. **The lineage registry lock, exclusive** (rank `LINEAGE_REGISTRY`).
4. **The lineage lock of the owner, exclusive** (rank `LINEAGE`).

Both are held for the whole command, git commands included: the registry lock cannot be
retaken once the lineage lock is held. The write flow's rule that no git command runs
under the registry lock exists so that admissions do not wait on git; here the global
exclusive admission already keeps every other admission out, so nothing waits on it.

On resume (§3.4), the owner is known only from the journal; the same locks are taken in
the same order.

### 3.3 Inspection — before any change

No state is modified until every check below passes. Each refusal is exit 1 with
`nothing cleaned` and names what was expected and what was found.

1. **Ids before paths.** The owner and every member id from the lineage file match
   `RUN_ID_PATTERN` before any path is built from them.
2. **The lineage is consistent with ha's own records:**
   - `branch == "ha/<owner>"`.
   - The owner's registry entry exists, its `lineage == owner`, and its `repository` is
     the lineage's.
   - `worktree == <owner run_dir>/wt`, and the run dir is under the runs root.
   - Neither `run_dir` nor `wt` is a symlink (`lstat`).
3. **Read-only git**, through the existing `git()` helper, which runs the tripwire:
   - `git worktree list --porcelain` in the repository says whether `wt` is registered.
   - It also says whether `refs/heads/ha/<owner>` is checked out in **another** worktree.
     That refuses: deleting the ref would leave that worktree on an unborn branch.
   - A `wt` that exists on disk but is not registered refuses: it is not ha's worktree.
   - `git rev-parse --verify --quiet refs/heads/ha/<owner>` gives the branch tip, or none.
4. **Quarantines.**
   - A repository quarantine for this `common_dir` is lifted only if its `run_id` is a
     member; otherwise it is another lineage's, and the command refuses.
   - The operator quarantine follows the same rule. It also counts as ours when it was
     published for a stale unconfined intent of a member.
   - An unreadable quarantine file refuses.
5. **The unconfined intent** is lifted only if its run is a member. It is necessarily
   stale: a live unconfined writer holds the global lock that §3.2 step 2 just obtained.
   An intent of a non-member refuses.

### 3.4 The journal

`<state>/cleanups/<owner>.json` is created once with `state.create_once`; each later update
goes through `state.publish`. It holds:

| Field | Content |
|---|---|
| `version` | `1` |
| `owner`, `members` | ids, validated as in §3.3 step 1 |
| `repository`, `common_dir` | from the lineage |
| `worktree`, `worktree_registered` | path and the §3.3 step 3 answer |
| `branch`, `tip` | `ha/<owner>` and the recorded tip, or `null` when the branch was absent |
| `base` | from the lineage, for the bundle |
| `keep_branch` | the flag |
| `lifted_at` | one UTC timestamp `%Y%m%dT%H%M%SZ`, shared by every file lifted |
| `files` | ordered list of `{path, sha256, size}`, paths relative to `<state>` |
| `residue` | `{archive: {path, sha256} or null, bundle: {path, sha256} or null}`, filled by step 1 |
| `steps` | `{save_residue, remove_worktree, delete_branch, lift_files}`, each `false` or `true` |
| `completed` | `false` until the last step is done |

**Resume.**

- When the journal exists, the command does not re-inspect the lineage: the lineage file
  may already be lifted. It loads the journal instead.
- The journal is validated like any state file: an unknown key, a wrong type, an id not
  matching `RUN_ID_PATTERN`, a path escaping `<state>`, or a branch other than
  `ha/<owner>` all make it `Unknown`, which refuses with `recover it by hand`.
- The command then runs the steps not yet done.
- A completed journal answers `already cleaned` with exit 0.
- The journal stays after completion as the audit record.

`--keep-branch` on a resume must match the journal's `keep_branch`; a mismatch refuses.

### 3.5 Steps

Each step checks, in this order:

1. **Already done**: the state the step leaves.
2. **Expected pre-state**: the state the journal recorded.
3. **Act**: run the step's action, then publish the journal with the step marked done.

A state that is neither already done nor the expected pre-state refuses with exit 1. The
refusal names the step, what was expected and what was found. The journal stays as it is,
so a retry resumes.

`GitTampered`, `subprocess.TimeoutExpired`, `OSError` and a non-zero git exit leave the
step not done, and the command exits 1 with the step named. One line per step goes to
stdout, `<step>: <what was done or found>`.

1. **save_residue.**
   - **Done** when the journal's `residue` entries exist with their recorded sha256.
   - **Act**, without any git command in the worktree. The tripwire case rewrites
     `wt/.git`, so `gitops.git` refuses to run there (`GitTampered`). A tampered
     repository may also carry filter or diff drivers that `git add` or `git diff` would
     execute.
     - When `wt` exists: a `tar.gz` archive of its whole content, untracked files
       included, `.git` excluded, symbolic links stored as links and never followed. It
       is written to `<state>/cleanups/<owner>/worktree.tar.gz`.
     - When `base` is known and `refs/heads/ha/<owner>` holds commits after it: a bundle
       `<state>/cleanups/<owner>/commits.bundle`, made by
       `git bundle create <file> <base>..refs/heads/ha/<owner>` from the repository
       root. Bundling packs objects and runs no filter or diff driver.
     - Each file is written to a temporary name then renamed, and its sha256 recorded.
   - **Nothing to save** (no worktree, no commits) records `null` and marks the step done.
2. **remove_worktree.**
   - **Done** when `wt` is absent and `git worktree list --porcelain` no longer names it.
   - **Expected pre-state**: `wt` present (not a symlink), or registered and missing.
   - **Act**: `shutil.rmtree(wt)`, which does not follow symbolic links, then
     `git worktree prune --expire=now` from the repository root.
     - No git command runs in `wt` itself, for the reason step 1 gives.
     - `git worktree remove` would also refuse a worktree whose `.git` file was
       rewritten.
     - `prune` only drops administrative entries whose directory is gone.
3. **delete_branch.**
   - Skipped (marked done) with `keep_branch`, and when the recorded `tip` is `null`.
   - **Done** when the ref is absent: that is a crash after the deletion.
   - **Expected pre-state**: the ref at the recorded `tip`, and checked out in no
     worktree.
   - **Act**: `git update-ref -d refs/heads/ha/<owner> <tip>`, a compare-and-delete that
     loses any race against a concurrent move.
   - A ref at another sha refuses: the branch was replaced since the journal was written.
4. **lift_files.**
   - Each file in `files` is renamed with one atomic `rename` to
     `<path>.lifted-<lifted_at>`.
   - **Done** for a file when the source is absent and the target is present with the
     recorded sha256.
   - **Expected pre-state** for a file: the source present with the recorded sha256, and
     the target absent.
   - The order is fixed:
     1. The stale unconfined intent, before the operator quarantine, so that no write can
        re-publish the quarantine from it.
     2. Member run records.
     3. The lineage file.
     4. The repository quarantine.
     5. The operator quarantine.
     6. The lineage lock, last, while this command holds it: renaming a lock someone else
        holds is the hazard the manual procedure warns about. The lock file has no
        content, so its identity is its existence.
   - No rollback: an interrupted lift is finished by the next run.
   - The step ends with `completed: true`.

Member run directories (reports, logs) are kept. The final line names them and the
residue files.

### 3.6 Ticket 925b07b6 — already fixed, no code change

Found while planning (spec amendment 1, §7):

- Ticket 925b07b6 is brain-v42 ticket 9ec19a4e, moved. v0.5.3 already fixed it with the
  ticket's option (c), in commit 55d51f0. `state.Missing` reads a lineage listed and then
  withdrawn as absent, in `lineage.of_repository`, `write_flow.check_repository` and
  `review_flow`.
- Race tests already pin it: `test_write_flow.py:775` and `test_review.py:1176`.
- Option (a) is impossible under the rank order. `_withdraw` runs while the write holds
  its lineage lock (rank 6), and the registry lock is rank 5.
- The ticket is resolved with this evidence; 0.5.4 changes nothing here.

### 3.7 `ha init [--print]` (lot 6)

The behaviour is the one the 0.5.3 spec (§3.6, D2) gave lot 6:

- It writes `roles.toml` and `workflows.toml` into the config directory only when absent.
- It never overwrites: exit 2 names the existing file.
- `--print` writes both to stdout instead.

| Name | Kind | Provider | Effort | Write | Context | Timeout | Model tier (comment only) |
|---|---|---|---|---|---|---|---|
| `judge` | role | codex | high | no | none | 1800 s | strongest |
| `closure` | role | codex | high | no | global | 1200 s | fast |
| `builder` | role | codex | medium | yes | full | 1800 s | fast |

No model name is written. Each codex role carries a commented `# model = "..."` line
saying which tier belongs there (strongest or fast). Models come from `models.toml` and

validation; a test asserts that.

### 3.8 Small items

**a. Unknown model id** (31b93dbd, formerly 74289428).

- Before the run starts, the resolved model id is checked against the catalogue entries
  for its provider.
- When the provider has a live list (opencode, agy, openrouter), the id is also checked
  against that list.
- An id found nowhere refuses with exit 2, before any provider starts.
- The refusal names up to three close ids the catalogue knows (`difflib`), and the file
  to edit.
- Without a catalogue, or for a provider the catalogue does not cover, nothing is
  checked: no regression for callers without one.

**b. `ha models` without a catalogue** (ac4f0768).

- Instead of exiting on the missing `catalog.toml`, the command prints the live lists of
  the queried providers (opencode, agy, openrouter) with their status.
- It then names the file to create for the rest.
- Exit 0 when at least one list is available, 2 otherwise.

**c. The `loopback` proof** (4fef3a23).

- A third proof kind, beside `isolation` and `confinement`, run by
  `ha prove <rail> --loopback`.
- A write run asks the agent to run a fixed script that binds `127.0.0.1:0`, connects to
  it and exchanges a token, with a bounded timeout.
- The proof records pass or fail per rail and installed version, like the existing kinds,
  and `ha providers` shows it.
- It gates nothing. The README's note about socket-based test clients points at it.

**d. `keys.py`.**

- The `KeysError` for a non-path entry names the entry and the rule, never the value: a
  key pasted where a path belongs must not reach stderr logs.
- `UnicodeDecodeError` and `RecursionError` from reading `keys.toml` become
  `KeysError(f"{path}: unreadable ({type})")`, as the `.env` reader already does.

## 4. Testing

Every test of §3.1-3.6 runs against a real git repository in `tmp_path`, with the existing
`World` fixtures. A crash is simulated by a hook that raises after a named step, in the
style of the existing `_crash_after`. One test per edge case:

| Edge case (56ce46f2, PR #246 rounds) | Test |
|---|---|
| Lineage paths trusted | A lineage file whose worktree, repository or owner disagrees with the owner's registry entry refuses, nothing changed |
| Symlinked run dir or worktree | Refuses before any git command |
| Member ids validated before paths | A member id with `../` makes the lineage `Unknown`; no path outside `<state>` is touched |
| Non-atomic archival | A crash in the middle of `lift_files`: the retry finishes it; no file is lifted twice or lost |
| Retry after partial failure | A crash after each step in turn: the retry completes and the final state is identical |
| Branch provenance | The branch moved after the journal: `delete_branch` refuses with expected vs actual |
| Crash after the branch deletion | Ref absent and step not marked: the retry marks it done and continues |
| Concurrent branch move | `update-ref -d` with a stale tip loses and refuses |
| Branch checked out in another worktree | Refuses at inspection and again at `delete_branch` |
| Stale unconfined intent | Lifted before the operator quarantine; the next write is admitted |
| A quarantine of another lineage | Refuses, nothing changed |
| Lock still held | A member holding its lifecycle lock refuses; the lineage lock is lifted last while held |
| `GitTampered`, `TimeoutExpired` | Each leaves the step not done, exit 1; the retry succeeds |
| Healthy lineage | `--force` refuses and names `ha clean` |
| Resume with a lifted registry entry | `RUN` resolves through the journal |
| Completed journal | Exit 0, `already cleaned` |
| Corrupt journal | `Unknown`, refuses, nothing changed |
| Residue | The archive restores tracked and untracked files, and symlinks stay links; the bundle passes `git bundle verify`; a worktree whose `.git` was rewritten is archived and removed with no git command run in it |
| Lock order | Every lock `ha clean --force` takes goes through `locks.held` / `admit_global`, so `_check_order` would raise on a violation; a resume takes the same order |

Small items: unit tests per behaviour above, plus `ha init` output that loads through
`roles.py` and `workflows.py`, and a `--print` byte-for-byte golden. The loopback proof
gets a unit test with a fake rail. The real rails are exercised in the release evidence,
not in CI.

## 5. Non-goals

- `ha abandon`, or any second verb for the same effect (Q107).
- Gating writes on the loopback proof, or a role field declaring socket needs.
- Model names in presets.
- Deleting run directories or lifted files: lifted state is kept for audit.
- The other open tickets on red-ha (G1-G6 for red-arena, the OpenRouter decisions
  provider, the review wrapper, the write sandbox, field reports): each needs its own
  design.
- Running `ha providers --update` (D6).

## 6. Success criteria

- Every row of §4 has a test that fails before the change and passes after it.
- `make ci` and `rail check` are green.
- On a scratch repository, a write forced into `compromised` is retired by
  `ha clean --force`, and a new write is then admitted with no manual step. This is
  recorded in the release evidence along with the release checklist of `CLAUDE.md`.
- The README replaces "lift it by hand" with `ha clean --force`, and keeps the manual
  procedure as the fallback when the cleanup itself refuses.

## 7. Amendments

**Amendment 1 (2026-10-02, found while writing the plan).** Three points of the reviewed
spec broke the lock rank order (`locks._check_order`):

- Several `LIFECYCLE` locks held at once.
- The registry lock retaken while the lineage lock was held.
- 925b07b6's option (a), taking the registry lock in `_withdraw` under the lineage lock.

Corrections:

- §3.2: one lifecycle lock (`RUN`), the other members probed with `is_free`; the registry
  lock, then the lineage lock, both held for the whole command.
- D3 and §3.6: 925b07b6 was already fixed in v0.5.3 by option (c), so there is no code
  change for it.
- §4: the 925b07b6 row is replaced by a lock-order row.
- §3.5 steps 1-2 run no git command in the worktree.
  - The reviewed spec built the residue patch with `git add -A` and `git diff` in `wt`,
    and removed `wt` with `git worktree remove`.
  - In the tripwire case, `gitops.git` raises `GitTampered` there, and a tampered
    repository could run filter drivers.
  - The residue is now a `tar.gz` archive of the worktree plus a bundle of the commits.
  - The worktree is removed with `rmtree`, then `git worktree prune --expire=now`.
